# Q6 [10 points]

The league director wants you to insert new records into the `teams` table. For all teams in 2024, insert a new record using the `franchID` as the `teamID`. If the insert fails due to a conflict, set the existing record's `attendance` to -1.

**File:** q6\_upsert.duckdb.sql

**Details:** We will evaluate by selecting all teams in 2024 from the table and sorting by each column in order.

```
SELECT yearID, lgID, teamID, franchID, teamRank, attendance
FROM teams
WHERE yearID = 2024
ORDER BY lgID, teamID, franchID, teamRank, attendance;
```

**Hints** Consider how you might be able to insert and update existing rows in a single statement.

After running the select statement, the following two rows should exist:

```
2024|AL|HOU|HOU|1|-1
2024|AL|KCA|KCR|2|1658347
```
# QA

## Q1
This Q6 is testing a very common database operation: **UPSERT** (INSERT + UPDATE).

Let's first understand what "insert fails due to a conflict" means.

---

### 1. What is an INSERT conflict?

A normal `INSERT` tries to create a **new tuple**.

For example:

```sql
INSERT INTO teams VALUES
(2024, 'AL', 'HOU', 'HOU', 'divID',1, 'name', 2835234);
```

The database checks all constraints.

The `teams` table has a primary key:

From previous questions:

```text
PRIMARY KEY(yearID, lgID, teamID)
```

So uniqueness is:

```
(yearID, lgID, teamID)
```

A conflict happens when the row you insert has the same primary key as an existing row.

---

Example:

Existing table:

```
yearID | lgID | teamID | franchID | attendance
------------------------------------------------
2024   | AL   | HOU    | HOU      | 2835234
```

You execute:

```sql
INSERT INTO teams 
VALUES
(2024, 'AL', 'HOU', 'HOU', 'divID',1, 'name', 2835234);


```

The database says:

```
ERROR:
duplicate key violates primary key constraint

Constraint Error:
Duplicate key "yearID: 2024, lgID: AL, teamID: HOU" violates primary key constraint.

```

because:

```
(2024, AL, HOU)
```

already exists.

That is the "conflict".

---

### 2. Why does the problem ask to insert using franchID as teamID?

Current 2024 data:

Example:

```
yearID | lgID | teamID | franchID | teamRank | attendance
----------------------------------------------------------
2024   | AL   | HOU    | HOU      | 1        | 2835234
2024   | AL   | KCA    | KCR      | 2        | 1658347
```

The instruction:

> For all teams in 2024, insert a new record using the `franchID` as the `teamID`.

means transform:

Original:

```
teamID = HOU
franchID = HOU
```

Insert:

```
teamID = franchID
```

For Houston:

```
new row:

yearID = 2024
lgID = AL
teamID = HOU
franchID = HOU
teamRank = 1
attendance = 2835234
```

No problem because:

```
(2024, AL, HOU)
```

already exists.

Therefore:

**conflict occurs.**

---

For Kansas City:

Existing:

```
yearID | lgID | teamID | franchID
----------------------------------
2024   | AL   | KCA    | KCR
```

Insert using franchID:

```
2024 | AL | KCR | KCR
```

The primary key becomes:

```
(2024, AL, KCR)
```

Does not exist.

Therefore:

```
INSERT succeeds
```

No update happens.

---

### 3. Why does the expected result show:

```
2024|AL|HOU|HOU|1|-1
2024|AL|KCA|KCR|2|1658347
```

Let's analyze.

#### Houston

Original:

```
2024|AL|HOU|HOU|1|2835234
```

Insert tries:

```
2024|AL|HOU|HOU|1|2835234
```

Conflict:

```
PRIMARY KEY:
(2024, AL, HOU)
```

The UPSERT says:

> if conflict happens, update existing record's attendance to -1

Therefore:

Before:

```
2024|AL|HOU|HOU|1|2835234
```

After:

```
2024|AL|HOU|HOU|1|-1
```

---

#### Kansas City

Original:

```
2024|AL|KCA|KCR|2|1658347
```

Insert using franchID:

```
2024|AL|KCR|KCR|2|1658347
```

No conflict.

So after UPSERT:

```
2024|AL|KCA|KCR|2|1658347
2024|AL|KCR|KCR|2|1658347
```

The problem statement only shows:

```
2024|AL|KCA|KCR|2|1658347
```

because the evaluation probably sorts/selects rows from the original schema state or only expects the conflict-updated rows. But conceptually the important point is:

* HOU → conflict → UPDATE attendance
* KCA → no conflict → INSERT new row

---

### 4. What SQL feature is being tested?

This sentence:

> Consider how you might be able to insert and update existing rows in a single statement.

is pointing to:

#### DuckDB UPSERT syntax

Equivalent concept:

```sql
INSERT INTO teams (...)
VALUES (...)
ON CONFLICT(primary_key)
DO UPDATE SET attendance = -1;
```

The database execution:

```
INSERT row
       |
       |
       v
Does primary key exist?
       |
   +---+---+
   |       |
  No      Yes
   |       |
 INSERT   UPDATE
```

---

### 5. Database concept connection

This is the same pattern used in production systems:

#### Example: user profile synchronization

Incoming data:

```
user_id | name
---------------
1001    | Alice
```

If user exists:

```
UPDATE
```

If user does not exist:

```
INSERT
```

called:

* UPSERT
* MERGE
* INSERT ON CONFLICT
* INSERT ... ON DUPLICATE KEY UPDATE

Different databases:

| Database            | Syntax                               |
| ------------------- | ------------------------------------ |
| PostgreSQL          | `INSERT ... ON CONFLICT`             |
| DuckDB              | `INSERT ... ON CONFLICT`             |
| SQLite              | `INSERT ... ON CONFLICT`             |
| MySQL               | `INSERT ... ON DUPLICATE KEY UPDATE` |
| SQL Server / Oracle | `MERGE`                              |

---

So the key insight for Q6:

The "conflict" is **not a data conflict in the business sense**. It means:

> The new row violates a uniqueness constraint (usually primary key), so the database cannot insert it as a new tuple.

For this Lahman schema:

```
PRIMARY KEY(yearID, lgID, teamID)
```

causes HOU to conflict, while KCR does not.
